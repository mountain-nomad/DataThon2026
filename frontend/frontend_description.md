# Frontend Specification — AI Cash Operations Monitoring

## 1. Product Overview

Веб-приложение для выявления потенциальных нарушений кассовой дисциплины на основании видеозаписей камер наблюдения с использованием локальных AI/ML-моделей.

Продукт должен демонстрировать два сценария:

1. **Video Inference** — пользователь загружает видеозапись и получает результат автоматического анализа.
2. **Monitoring Dashboard** — пользователь наблюдает за сеткой камер, статистикой обнаруженных событий и отдельными эпизодами возможных нарушений.

Интерфейс должен восприниматься как единый продукт, а не как два отдельных демо.

### Общие требования

- Desktop-first, с адаптацией под небольшие экраны.
- Видеоматериалы камер преимущественно горизонтальные, с ракурсом сверху.
- Сохранять оригинальные пропорции видео, не обрезать значимые части изображения.
- Все видеоматериалы и AI-инференс обрабатываются локально.
- Не использовать облачные AI API и внешние сервисы обработки видео.
- Не реализовывать распознавание или идентификацию лиц.
- Не требуется авторизация, история проверок или экспорт отчётов.
- Интерфейс должен различать **потенциальное нарушение, обнаруженное AI**, и подтверждённое человеком событие.

## 2. Routing

Приложение содержит ровно три основные страницы.

```text
/
├── /demo-inference
└── /demo-dashboard
```

Обеспечить навигацию между всеми страницами, включая возможность вернуться на главную.

## 3. Page 1 — Landing Page

**Route:** `/`

### Назначение

Представить AI-сервис и дать пользователю возможность выбрать демонстрационный сценарий.

### Структура

**Hero section**

- Название продукта.
- Краткое описание: AI-powered video monitoring for cash operations.
- Объяснение основной ценности: автоматическое выявление подозрительных действий, точная локализация событий и предоставление доказательств для проверки человеком.

## 4. Page 2 — Video Inference

**Route:** `/demo-inference`

### Назначение

Позволить пользователю загрузить ранее не анализировавшийся видеофайл и увидеть результат работы модели.

### 4.1. Upload

Реализовать загрузку видео посредством drag-and-drop и file picker.

Требования:

- Принимать `.mov`.
- Проверять расширение файла и корректность загрузки.
- Отображать название и размер выбранного файла.
- Позволять заменить файл до запуска.
- Кнопка `Analyze Video` инициирует обработку.
- Пока видео анализируется, повторный запуск той же задачи недоступен.

### 4.2. Processing State

После запуска отображать:

- Статус `Uploading`, `Processing`, `Completed` или `Failed`.
- Progress indicator.
- Сообщение о том, что выполняется AI-анализ.

Не показывать выдуманный процент завершения. Если backend не передаёт фактический прогресс, использовать indeterminate progress indicator.

Frontend отправляет файл на backend, получает `job_id` и периодически проверяет статус задачи.

### 4.3. Inference Results

После успешного завершения отображать:

**Video player**

- Исходное загруженное видео.
- Play / pause.
- Seekbar и текущий таймкод.
- Возможность перейти непосредственно к обнаруженному событию.
- Визуальные маркеры событий на timeline, если события обнаружены.

**Overall verdict**

Возможные состояния:

- `No violations detected`
- `Potential violations detected`

**Violation list**

Каждое событие представляется отдельной карточкой со следующими данными:

- Violation type.
- Timecode в исходной видеозаписи.
- Description — что конкретно наблюдается на видео.
- Evidence frames — 1–3 кадра-доказательства.
- Referenced rule — название нормативного документа и пункт/раздел, если сопоставление подтверждено.
- Action `Jump to timestamp` — перемотка основного видео к событию.

Если нарушений не обнаружено, показывать соответствующий empty state без пустых карточек.

Не представлять вывод модели как окончательно установленное нарушение.

## 5. Page 3 — Monitoring Dashboard

**Route:** `/demo-dashboard`

### Назначение

Продемонстрировать сценарий мониторинга кассовых операций с нескольких камер и последующего разбора обнаруженных событий.

На хакатоне используются демонстрационные записи. Интерфейс может имитировать многокамерный мониторинг, но не должен обозначать заранее записанное видео как настоящий live stream.

### 5.1. Camera Grid

Основной блок — сетка **4 × 4**, всего 16 камер.

```text
CAM 01    CAM 02    CAM 03    CAM 04
CAM 05    CAM 06    CAM 07    CAM 08
CAM 09    CAM 10    CAM 11    CAM 12
CAM 13    CAM 14    CAM 15    CAM 16
```

Каждая камера отображается в отдельной видео-карточке.

Содержимое:

- Горизонтальный video preview.
- Camera ID.
- Статус источника: `Demo`, `Playing`, `Unavailable`.
- Индикатор обнаруженного потенциального нарушения при наличии события.

Поведение:

- Видео может воспроизводиться в цикле.
- При выборе камеры открыть увеличенный просмотр с возможностью управления воспроизведением.
- При клике на индикатор события можно перейти к соответствующему эпизоду в нижней секции.
- Не искажать изображение ради заполнения карточки.

**Video orientation:** по умолчанию использовать aspect ratio `16:9` для горизонтальных камер видеонаблюдения, с сохранением исходных пропорций изображения. Если реальный файл имеет другое соотношение сторон, использовать `object-fit: contain`, а не `cover`.

Сетка на desktop — 4 колонки. Для узких экранов допускается адаптивное сокращение числа колонок.

### 5.2. Violation Statistics

Ниже сетки камер расположен блок агрегированной статистики обнаруженных событий.

Минимальные показатели:

- Total Detected Events — число обнаруженных эпизодов.
- Cameras With Detections — число камер, на которых обнаружены события.
- Pending Review — эпизоды, ещё не рассмотренные человеком.
- False Positives — количество событий, помеченных пользователем как ложные срабатывания.

Дополнительно допускается breakdown по типам нарушений.

Все показатели должны рассчитываться на основании единого списка событий, а не содержать независимые захардкоженные значения.

### 5.3. Detected Violation Episodes

Под статистикой расположен вертикальный список эпизодов обнаруженных нарушений.

**Каждый эпизод — горизонтальная карточка.**

```text
┌────────────────────────────────────────────────────────┐
│                                                        │
│  ┌────────────────┐  Process Name                      │
│  │                │  Violation Type                    │
│  │  VIDEO CLIP    │  Timecode: 00:12                   │
│  │                │  Camera: CAM 03                    │
│  │                │                                     │
│  └────────────────┘  Description of detected event     │
│                                                        │
│                        [Mark as False Positive]        │
└────────────────────────────────────────────────────────┘
```

**Слева: Episode video**

- Короткий фрагмент исходного видео с обнаруженным событием.
- Горизонтальная ориентация.
- Play / pause и seekbar.
- При открытии эпизода пользователь видит контекст события, а не только один кадр.

**Справа: Event information**

- Process Name — наименование кассового процесса.
- Violation Type — классификация потенциального нарушения.
- Camera ID — источник видеозаписи.
- Episode Timecode — время нарушения относительно начала короткого видео.
- Source Timecode — время нарушения относительно начала оригинальной записи.
- Description — наблюдаемое действие и причина срабатывания.
- Evidence frame(s).
- Referenced Rule / Regulatory Source.

**Action: Mark as False Positive**

По нажатию:

1. Эпизод получает review status `false_positive`.
2. Карточка визуально отображает новый статус.
3. Счётчик False Positives обновляется.
4. Эпизод остаётся доступен для просмотра.
5. Пользователь может отменить отметку.

Отметка должна влиять на статистику проверки человеком, но не переписывать исходный вывод модели.

### 5.4. Empty and Error States

Поддержать ситуации:

- Нет обнаруженных эпизодов.
- Видеокамера недоступна.
- Фрагмент видео не загрузился.
- Отсутствует кадр-доказательство.
- Для события не найден нормативный источник.

В последнем случае показывать отсутствие подтверждённой ссылки, а не генерировать фиктивную норму.

## 6. Frontend Data Models

Обе демонстрационные страницы должны использовать согласованные модели данных.

### Camera

```ts
type Camera = {
  id: string;
  name: string;
  videoUrl: string;
  status: "demo" | "playing" | "unavailable";
};
```

### ViolationEvent

```ts
type ViolationEvent = {
  id: string;
  cameraId?: string;

  processName?: string;
  type: string;
  description: string;

  // Seconds relative to original video
  timecodeSec: number;

  // Clip begins at this original-video timestamp
  clipStartSec?: number;
  clipUrl?: string;

  evidenceFrames: {
    timestampSec: number;
    imageBase64: string;
  }[];

  regulatorySource?: {
    documentTitle: string;
    section?: string;
    url?: string;
  };

  reviewStatus:
    | "pending"
    | "false_positive";
};
```

Для короткого эпизода вычислять локальный таймкод:

`episodeTimecodeSec = timecodeSec - clipStartSec`

Результат должен находиться в границах длительности клипа.

Не путать этот таймкод с `timecode_sec`, который ожидается API жюри и всегда относится к исходному видео.

## 7. API Integration

Использовать предусмотренный заданием API.

**Upload and analyze**

`POST /api/v1/analyze`

Request: `multipart/form-data`, поле `file`.

Response содержит `job_id`.

**Check processing status**

`GET /api/v1/jobs/{job_id}`

Поддерживаемые backend statuses:

- `processing`
- `done`
- `failed`

При `done` обработать `verdict`, `violations`, `timecode_sec`, `description`, `evidence_frames`.

Реализовать polling примерно каждые 2–3 секунды. Предусмотреть обработку сетевых ошибок и истечения пяти минут без результата.

Для браузерного frontend использовать локальный backend/proxy. API-ключ `X-API-Key` не должен находиться в публичном JavaScript bundle.

Поля `processName`, `clipUrl`, `regulatorySource` и `reviewStatus` не входят в обязательный API жюри. Они могут поступать из дополнительного backend endpoint, локального демонстрационного набора или слоя адаптации данных.

Не изменять обязательный контракт API жюри ради отображения дополнительных полей frontend.

## 8. Video Handling

Основные требования:

- Поддержка загрузки `.mov`.
- Корректное отображение горизонтальных CCTV-записей.
- Локальная обработка файлов.
- Возможность перехода к заданному таймкоду.
- Корректная работа с короткими видеоклипами.
- Не допускать искажения, растяжения и нежелательного кадрирования.

Важно: браузер может не поддерживать видеокодек внутри `.mov`. При необходимости backend должен локально формировать совместимый preview, например MP4/H.264, сохраняя оригинальный файл для inference.

Для 16 камер предусмотреть оптимизацию воспроизведения: не запускать без необходимости одновременное декодирование всех видеопотоков в полном разрешении. Использовать облегчённые demo-превью, ограничивать загрузку и активное воспроизведение.

## 9. Implementation Scope

### MVP — обязательно

- Три работающих маршрута.
- Landing page с двумя переходами.
- Upload `.mov` и реальный запуск inference.
- Processing / done / failed states.
- Результат с таймкодами, описанием, evidence frames и доступным нормативным обоснованием.
- Monitoring Dashboard с сеткой из 16 камер.
- Агрегированная статистика.
- Горизонтальные карточки видеоэпизодов.
- Отметка False Positive и обновление статистики.
- Корректные empty/error states.

### Дополнительные улучшения при наличии времени

- Timeline markers на основном видео.
- Фильтр эпизодов по типу нарушения, камере и review status.
- Синхронизация выбранной камеры с карточкой события.
- Полноэкранный режим выбранной камеры.

## 10. Design Instructions

Use the existing project design skills for all visual decisions.

Do not independently reinvent the design system.

Prioritize:

- Clarity of monitoring information.
- Readability of CCTV footage.
- Fast access from detected event to video evidence.
- Clear distinction between AI detection and human review.
- Consistent interaction patterns across both demos.

The frontend must be demonstrable using local prerecorded video assets without requiring any production banking infrastructure.
