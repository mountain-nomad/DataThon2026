## 1. Product goal and scope

**[MUST — ForteBank]** Создать работающий сервис, в котором пользователь загружает новое видео с кассовыми операциями, автоматически получает анализ визуально наблюдаемых возможных нарушений и может проверить вывод по времени события, кадрам-доказательствам и нормативным источникам.

Сервис должен включать:

1. Готовый веб-интерфейс для загрузки видео, отображения статуса и результата.
2. Рабочую серверную часть без необходимости вручную запускать скрипты после каждой загрузки.
3. Анализ визуальных действий по видео; возможно несколько нарушений в одном ролике.
4. Публично доступный API по точно указанному в разделе 4 контракту для автоматической проверки жюри.
5. Проверяемые ссылки на открытые нормы Республики Казахстан и объяснение связи с наблюдаемым действием.

**[PROJECT DECISION]** Frontend уже существует. ML inference существует в отдельной папке `ML/`. На текущем этапе **разрабатываем backend**, не переписывая существующий frontend или логику ML-модели.

## 2. Input data and constraints

| Attribute | Requirements / known dataset characteristics |
|---|---|
| Upload format | **[MUST — ForteBank]** `.mov` |
| Multipart field | **[MUST — ForteBank]** `file` |
| Typical file size | Около **29 МБ**. Это ориентир из FAQ, **не установленный организатором точный максимум**. |
| Clip duration | Обучающий датасет: примерно 10–145 секунд. |
| Frame rate | В датасете от 29 FPS. |
| Audio | Записи без звука; анализ строго визуальный. |
| Camera | В обучающих данных постановочная съёмка сверху, одна касса и одна камера; финальная проверка может быть под другим углом. |
| Labels | В обучении размечены наличие нарушения и таймкод; тип нарушения командам не предоставляется. |
| Dataset size | Не менее 40 роликов в обучающем наборе. |
| Unseen data | В тесте возможны ранее неизвестные типы нарушений. |

**[MUST — ForteBank]** Не использовать аудио и не выполнять распознавание/идентификацию лиц. Не использовать тестовые ролики для обучения, не публиковать их и не передавать третьим лицам. Использовать датасет только в рамках хакатона.

**[RECOMMENDED]** Валидировать расширение и фактическую читаемость/контейнер видео, но не делать один фиксированный MIME type обязательным условием: клиенты могут передавать `.mov` с разными допустимыми MIME-заголовками. Лимиты сервера на размер тела запроса и timeout конфигурируются так, чтобы принять типичные файлы из задания; не выдавать ориентир «29 МБ» за точный лимит организатора.

## 3. Mandatory user journey

**[MUST — ForteBank]**

1. Пользователь открывает веб-интерфейс и загружает видео.
2. Сервис автоматически запускает обработку и показывает статус.
3. После обработки отображает **ровно один** вердикт на всё видео: «Нарушение не обнаружено» или «Обнаружены признаки возможных нарушений».
4. Для **каждого** предполагаемого нарушения сообщает тип, таймкод и понятное описание.
5. Показывает **1–3 JPEG кадра-доказательства** для каждого нарушения (для API — base64).
6. Объясняет, какие наблюдаемые действия вызывают подозрение, без недоказуемых предположений.
7. Указывает применимое правило и источник: название документа, пункт/раздел, если они доступны; не выдумывает ссылки и нормативные формулировки.
8. Предоставляет тот же анализ через API для проверки жюри.

Результат — **помощь человеку в проверке**, а не окончательное юридическое или дисциплинарное заключение. Нельзя выводить нарушение из сведений, которые невозможно наблюдать по видео (например, корректность банковской проводки или системной сверки).

**[PROJECT DECISION]** В существующем demo frontend предусмотрены стадии: распознавание сценария → распознавание нарушения → локализация нарушения. Это UI/implementation flow команды, **не отдельное обязательство из ТЗ**. Backend может передавать внутренний прогресс, не нарушая публичный API-контракт.

## 4. Jury API — exact mandatory contract

### 4.1 Authentication

**[MUST — ForteBank]** Все обращения к публичному API жюри требуют `X-API-Key` с выданным команде ключом. Запрос с отсутствующим или неверным ключом должен отклоняться.

**[RECOMMENDED]** Проверять ключ на сервере, хранить секрет в переменных окружения, возвращать `401 Unauthorized` при неверном/отсутствующем ключе, не писать сам ключ в логи.

### 4.2 POST `/api/v1/analyze`

**[MUST — ForteBank]**

- Request: `multipart/form-data`, поле `file`, файл `.mov`.
- Response: JSON с `job_id` для последующего опроса.
- Backend принимает **байты файла** из POST; клиенту не требуется предварительно загружать файл в объектное хранилище.

Request example (соответствует ТЗ):

```bash
curl -X POST https://team.example.kz/api/v1/analyze \
  -H "X-API-Key: <key>" \
  -F "file=@video_017.mov"
```

Response example (`job_id` — единственное обязательное поле, названное в ТЗ для POST):

```json
{
  "job_id": "3f2a9c1e"
}
```

**[RECOMMENDED]** Допустимый ответ — HTTP `202 Accepted`, если анализ идёт асинхронно. Не утверждать, что именно этот статус-код предписан ТЗ: конкретный HTTP-код успешного POST в источнике не указан.

### 4.3 GET `/api/v1/jobs/{job_id}`

**[MUST — ForteBank]** Возвращает статус обработки `processing`, `done` или `failed`; при завершении — результат.

Processing response example:

```json
{
  "job_id": "3f2a9c1e",
  "status": "processing"
}
```

Done response — **структура организатора**:

```json
{
  "job_id": "3f2a9c1e",
  "status": "done",
  "verdict": "violation",
  "violations": [
    {
      "type": "Название типа нарушения",
      "timecode_sec": 44.2,
      "description": "Что видно на видео и почему это может быть нарушением",
      "evidence_frames": [
        {
          "timestamp_sec": 44.2,
          "image_base64": "/9j/4AAQ..."
        }
      ]
    }
  ]
}
```

Done response, если нарушения отсутствуют:

```json
{
  "job_id": "3f2a9c1e",
  "status": "done",
  "verdict": "no_violation",
  "violations": []
}
```

| JSON field | Type / exact meaning |
|---|---|
| `job_id` | Идентификатор задания, совпадающий с идентификатором, полученным из POST. |
| `status` | Один из `processing`, `done`, `failed`. |
| `verdict` | При `done` — **строго** `no_violation` или `violation`, вердикт на весь ролик. |
| `violations` | Массив объектов, пустой для `no_violation`. В ролике допустимо несколько нарушений. |
| `violations[].type` | Название типа предполагаемого нарушения. |
| `violations[].timecode_sec` | Число: секунды от начала видео. |
| `violations[].description` | Наблюдаемое действие и почему оно может свидетельствовать о нарушении. |
| `violations[].evidence_frames` | Массив из **1–3** кадров-доказательств. |
| `evidence_frames[].timestamp_sec` | Секунда, соответствующая доказательному кадру. |
| `evidence_frames[].image_base64` | Действительный JPEG в base64; не URL, путь или placeholder. |

**[MUST — ForteBank]** ТЗ предусматривает ровно два значения `verdict`. Не добавлять `insufficient_data`, `unknown`, `not_sure` и иные вердикты в ответ для жюри. `failed` является **статусом задания**, а не третьим вердиктом.

**[RECOMMENDED]** При ошибке задания возвращать `status: "failed"` с безопасным для клиента описанием ошибки; форма дополнительного поля ошибки организатором не регламентирована. Не возвращать вымышленный результат, если inference не был выполнен.

### 4.4 Time limit

**[MUST — ForteBank]** Если сервис недоступен или не вернул результат в течение **5 минут**, ролик засчитывается как необработанный. Асинхронность endpoint не снимает этот лимит. В финале будет проверяться минимум 5 видеороликов.

**[RECOMMENDED]** Установить внутренний дедлайн обработки с запасом до 5 минут, контролировать зависания inference и обеспечивать быстрый ответ polling endpoint. Измерять end-to-end время от подачи видео до `done`.

### 4.5 API compatibility rules

1. **[MUST — ForteBank]** Не переименовывать `/api/v1/analyze` и `/api/v1/jobs/{job_id}`.
2. **[MUST — ForteBank]** Не менять имена полей, enum-значения и формат base64 evidence.
3. **[RECOMMENDED]** Для автоматического жюри отвечать минимальной строго совместимой JSON-схемой, без обязательных для клиента новых полей.
4. **[PROJECT DECISION]** Дополнительные endpoint для frontend/storage допустимы, если они **не заменяют и не ломают** два обязательных endpoint.

## 5. Business rules and normative references

**[MUST — ForteBank]**

- Типы нарушений команда определяет самостоятельно; закрытого перечня нет.
- Использовать открытые нормативные акты **Республики Казахстан** (например, НБРК, `adilet.zan.kz`). FAQ допускает также ссылки на открытые документы других банков; основной нормативный контекст — РК.
- Не выдумывать документ, норму, номер пункта или юридическую квалификацию.
- Сопоставлять **конкретное наблюдаемое действие → потенциальное нарушение → проверяемый источник**.
- Сервис обязан объяснить, что видно в видео и почему действие **может** указывать на нарушение.
- Не делать выводы о невидимых действиях, системных данных или скрытых процессах.

**Важно о схеме:** пункт о нормативном источнике **есть в пользовательских требованиях ТЗ**, но в **JSON-примере API организатора поля для ссылки на норму нет**. Сохранить точную схему для жюри; поддерживать нормативную ссылку во внутренней структуре результата и отображать в frontend. Не добавлять обязательное `rule_reference` в контракт жюри без подтверждения совместимости.

**[RECOMMENDED]** Внутренняя запись нарушения может включать `rule_title`, `rule_section`, `rule_url`, `observation` и `evidence_frames`. Это **предлагаемая внутренняя модель**, а не поля, заданные ForteBank.

## 6. Architecture: source requirements vs existing implementation

### 6.1 Mandatory execution and portability

**[MUST — ForteBank]**

- Все AI-модели выполняются **локально внутри развёрнутого командой сервиса**.
- Нельзя отправлять видео, кадры или их описания в облачные AI/LLM/VLM/recognition API.
- После первоначальной загрузки весов обработка видео **не должна требовать доступа в интернет**.
- Решение должно быть переносимым во внутренний контур банка.
- Нужен публичный URL frontend и API для удалённого жюри; **публичная доступность входного API не означает разрешения использовать внешние AI API**.
- Предобученные модели и готовый код допускаются, если open-source лицензия разрешает коммерческое использование. Использование запрещённых готовых решений/облачных API может привести к дисквалификации.

### 6.2 Current project plan (NOT organizer-approved)

**[PROJECT DECISION]** В команде на данный момент обсуждался следующий путь:

```text
Frontend
  -> POST /api/v1/analyze (multipart .mov)
  -> Backend
  -> Supabase Storage (persist video, generate access link)
  -> ML/ inference function (prompts + video)
  -> RunPod endpoint hosting VLM
  -> Backend result
  -> GET /api/v1/jobs/{job_id}
```

**BLOCKER — incompatibility with ForteBank requirements:**

1. **RunPod inference через внешний VLM endpoint** противоречит требованию полностью локального выполнения модели без облачного AI API. Нельзя считать такой deployment соответствующим ТЗ.
2. **Внешний Supabase Storage** создаёт риск передачи тестовых видео третьей стороне и зависимости от интернета, что несовместимо с требованиями по обращению с тестовыми видео и офлайн-переносимости. ТЗ не даёт отдельного прямого разрешения на этот способ хранения.
3. Не скрывать эти проблемы и не подменять требование локальности утверждением, что «модель наша» или «API приватный».

**Для соответствующей ТЗ конкурсной сборки** использовать локальное файловое/объектное хранилище внутри доверенного развёртывания и локально обслуживаемую VLM-модель. Например, локальный диск или самостоятельно развёрнутый объектный storage — варианты реализации, а **не требование** конкретной технологии. Публичным остаётся только входной API команды.

**До решения этого противоречия:** Supabase + RunPod можно рассматривать только как отдельный экспериментальный путь разработки на разрешённых нетестовых данных; это **не подтверждённая соответствующая регламенту конкурсная архитектура**. Не отправлять конкурсные тестовые видео в эти сервисы.

### 6.3 Boundaries between modules

**[PROJECT DECISION]**

- Backend отвечает за HTTP API, авторизацию по API key, валидацию, хранение/получение видео, жизненный цикл job и выдачу результатов.
- Папка `ML/` остаётся владельцем существующей inference-функции. Не перемещать в backend VLM model code и не менять промпты без отдельной задачи.
- В будущей интеграции backend вызывает `ML/` через согласованный адаптер, передающий путь к доступному видео/его содержимое и необходимые промпты. Точная сигнатура определяется **по существующему коду**, а не придумывается заново.
- Frontend остаётся без изменений в текущей фазе.
- Не встраивать поддельные AI-ответы и не объявлять job успешным при отсутствии реально полученного результата inference.

## 7. Backend implementation plan

### Phase 1 — current scope: video upload and persistence

**[PROJECT DECISION]** Приоритет текущего задания — рабочий POST → сохранённое видео → доступ к файлу для последующего анализа. Это промежуточный этап; сам по себе он **не выполняет весь конкурсный сценарий**.

Backend должен:

1. Принять `.mov` через `POST /api/v1/analyze`, `multipart/form-data`, поле `file`.
2. Проверить `X-API-Key`; без валидного ключа не принимать видео.
3. Проверить присутствие и допустимость файла; аккуратно обработать повреждённые/пустые запросы.
4. Создать уникальный `job_id`, создать запись job и связать её с сохраняемым видео.
5. Сохранить исходные байты без перекодирования в настроенном backend storage.
6. Использовать уникальное имя объекта и хранить стабильный storage key/path, а не только истекающий URL.
7. Сделать видео доступным **самому backend** по локальному пути или защищённому URL (в зависимости от выбранного storage), чтобы позднее передать его в `ML/`.
8. Вернуть совместимый JSON `{"job_id":"..."}` после успешного принятия и сохранения файла.
9. Реализовать `GET /api/v1/jobs/{job_id}` со статусом `processing` / `failed` для диагностики первой фазы; `done` допустим только после настоящего inference и готового результата.
10. Обработать ошибки валидации, storage, отсутствующий job и сбои чтения; не оставлять неконсистентные «успешные» задания.
11. Не выдавать незащищённые ссылки на видео жюри или сторонним пользователям.
12. Документировать нужные переменные окружения и пример `curl`.

**Storage abstraction [RECOMMENDED]:** изолировать реализацию за `VideoStorage` или эквивалентным интерфейсом `save()`, `get_local_or_readable_reference()`, `delete()`. Это позволит начать с Supabase в отдельном экспериментальном окружении и заменить его локальным storage в конкурсной сборке, не меняя jury API.

**Для обсуждаемого Supabase-адаптера [PROJECT DECISION]:**

- Загружать файл в Supabase Storage **только backend-сервисом**.
- Не передавать frontend Supabase service role key.
- При приватном bucket использовать короткоживущие signed URL, если frontend необходим просмотр; у job хранить объектный путь.
- **Не** подменять endpoint жюри на прямую загрузку в Supabase.
- Не использовать удалённое хранилище для тестовых видеозаписей жюри без подтверждённого разрешения организатора.

**Link semantics:** фраза «ссылка на видео» в плане команды означает внутренний адрес/ссылку доступа к сохранённому объекту. ТЗ ForteBank **не** требует добавлять `video_url` в response жюри. Если frontend нуждается в URL, оформить отдельный внутренний API/механизм доступа, не нарушая внешнюю схему.

### Phase 2 — integrate real ML inference (not current development scope)

1. Backend запускает existing `ML/` inference после успешного сохранения видео.
2. Преобразует результат ML в нормализованный список предполагаемых нарушений.
3. Валидирует `timecode_sec` относительно длительности ролика и наличие реальных доказательных кадров.
4. Извлекает 1–3 JPEG-кадра из исходного видео на релевантных таймкодах и кодирует их base64.
5. Выдаёт вердикт `violation` или `no_violation` и соответствующие `violations`.
6. Переводит job в `done` лишь после сборки полного валидного JSON; при ошибке — в `failed`.
7. Обеспечивает укладывание полной обработки в лимит 5 минут.
8. В конкурсном deployment вызывает **локально размещённую** ML-модель, без запрещённого внешнего RunPod AI endpoint.

### Phase 3 — hardening and demo readiness

- Проверить frontend flow и статусы, несколько нарушений в одном видео, отсутствие нарушений и ошибки.
- Проверить производительность на роликах, аналогичных тестовым, и переносимость без интернета после загрузки весов.
- Подготовить руководство по запуску, архитектуру, перечень типов нарушений, нормативные источники, ограничения и известные ошибки.

## 8. Nonfunctional and security requirements

**[MUST — ForteBank]**

- Публичный адрес frontend и публичный адрес API, доступный жюри удалённо.
- API ключ в `X-API-Key` и отклонение запросов с неверным ключом.
- Результат не позже 5 минут для зачёта ролика.
- Отсутствие внешних облачных AI API и зависимости inference от интернета.
- Ни загрузки тестовых видео в публичный доступ, ни использования для обучения, ни передачи третьим лицам.

**[RECOMMENDED]**

- Не логировать видео, base64 кадров, промпты с чувствительной информацией или API-ключи.
- Не допускать path traversal, коллизий имён, выполнения содержимого загруженного файла и неограниченных загрузок.
- Сохранить атомарную/восстанавливаемую связь `job_id` с storage path; продумать очистку временных файлов.
- Отделить внутренние диагностические логи от внешнего JSON-контракта.
- Ограничить доступ к оригинальным видео и срок их хранения в соответствии с разрешённым использованием.

## 9. Tests and acceptance criteria

### Phase 1 checks — backend upload

- [ ] Валидный POST с `.mov` и `X-API-Key` возвращает JSON с непустым `job_id`.
- [ ] Полученный файл действительно существует в выбранном storage; байты читаются backend.
- [ ] Полученный `job_id` ассоциирован с корректным объектом и доступен через `GET /api/v1/jobs/{job_id}`.
- [ ] Два файла с одинаковым исходным именем не перезаписывают друг друга.
- [ ] Отсутствующий/неверный API-ключ отклоняется.
- [ ] Запрос без `file`, пустой файл и недопустимое расширение обрабатываются предсказуемо.
- [ ] Отказ storage возвращает ошибку и не создаёт фиктивно успешную загрузку.
- [ ] Контракт для жюри не зависит от URL Supabase и не требует direct-to-storage upload.
- [ ] `Backend Description.md` и переменные окружения обновлены по реальной реализации.
- [ ] Выбранный storage для конкурсной сборки удовлетворяет требованиям локальности и обращения с тестовыми видео.

### Full product checks — before judging

- [ ] POST + polling GET возвращают `done` и один из **двух** официальных вердиктов.
- [ ] Для `no_violation` возвращается `violations: []`.
- [ ] Для каждого нарушения есть type, numeric timecode, description и 1–3 валидных JPEG base64 кадра.
- [ ] JPEG действительно соответствует указанному фрагменту видео.
- [ ] При нескольких нарушениях каждое отражено отдельным элементом массива.
- [ ] UI показывает применимое правило/источник для каждого предполагаемого нарушения.
- [ ] Не выполняется распознавание лиц или анализ аудио.
- [ ] Полное выполнение для ролика укладывается в 5 минут.
- [ ] Нет обращений к запрещённым облачным AI API и передачи тестовых видео третьим лицам.
- [ ] Сервис способен обрабатывать ролики с изменённым ракурсом без жёсткой привязки к единственной постановке.
